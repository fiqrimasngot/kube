# Cluster operations context

Hermes can operate two independent cluster repositories:

- `fiqrimasngot/kube` at `/opt/data/workspace/kube`
- `dugeo/it-k8s` at `/opt/data/workspace/kube-kl/k8s`

## Cluster clients

- Run cluster commands from the target repository. The Hermes wrappers select the matching configuration from the current working directory.
- `/opt/data/workspace/kube`: kubeconfig is `/opt/data/workspace/kube/kubeconfig`; talosconfig is `/opt/data/workspace/kube/talos/talosconfig`.
- `/opt/data/workspace/kube-kl/k8s`: kubeconfig is `/opt/data/workspace/kube-kl/k8s/kubeconfig`; talosconfig is `/opt/data/workspace/kube-kl/k8s/talos/talosconfig`.
- Before cluster work, verify access with `kubectl get nodes` and `talosctl version --short`.
- Never print, commit, or copy the contents of kubeconfig, talosconfig, token, certificate, or credential files.

## GitOps

- Treat repository changes and live cluster changes as separate layers.
- Render affected Kustomizations before proposing or applying a GitOps change.
- Do not commit or push unless the user explicitly asks.

## Writing style

- Write new documentation and any documentation you substantially revise in simple, everyday English.
- Sound direct, practical, and informal, while keeping commands, identifiers, warnings, and technical facts exact.
- Use short sentences and paragraphs, active voice, and sentence-case headings. Explain unfamiliar terms the first time they appear.
- Start with what the reader needs to do or know. Include exact commands and expected results when they help the reader verify a step.
- Do not copy spelling mistakes to imitate the user. Do not add corporate wording, filler, decorative emojis, or AI-style phrases such as "delve," "pivotal," or "in conclusion."
- Do not rewrite unrelated documentation only to change its tone. Apply this style when creating a document or when the task already requires editing it.

## Commit message style

- When the user asks for a commit, write a lowercase, plain-English imperative subject that says what the change does.
- Keep the subject focused on one outcome and at most 72 characters. Do not add an emoji or a Conventional Commit prefix such as `feat:` or `fix:` unless an automated workflow requires that format.
- Examples: `add study planner reminder api` and `fix hermes profile config mounts`.
- Add a short body only when the reason, risk, or verification would otherwise be unclear.
- These style rules do not grant permission to commit or push; the GitOps rule above still requires the user's explicit request.
